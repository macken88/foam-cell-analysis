# GUI 設計ガイドライン

[AGENTS.md](../../AGENTS.md) の「6. GUI」を補足する。利用者が画面をぱっと見ただけで、何ができて、押すと何が起きるかが分かることを目指す。

## 進め方

1. 新しい画面や大きな変更は、まず ASCII のモックを設計書に書き、ユーザーの承認を得る。
2. 実装したら、スクリーンショットと下のチェックリストでレビューする。

## ボタン名・ラベル

- 何が起きるかが分かる名詞＋動作の形にする（「実行」「OK」だけにしない）。
- 意味が通じるなら助詞は省く。漢字が続いても、日本人がぱっと見で読めるならそのままでよい。
- 助詞を残すのは、省くと意味が曖昧になる場合だけ。

| 避ける | 使う |
|---|---|
| 実行 | 学習開始 |
| 学習を開始 | 学習開始 |
| 結果を保存 | 結果保存 |
| 前回の設定を読み込み | 前回設定の読込み／前回設定読込み |
| 選択中の画像を削除 | 選択画像を削除 |

- 同じものは画面が違っても同じ語で呼ぶ。新しい用語を作るときは、既存の画面で使っている語を先に確認する。
- 冗長な言い回し（「〜を行います」「〜することができます」）を避け、短く書く。

## 情報量

- 主要な操作は1画面に1つとし、見た目で他と区別する。
- 閲覧・操作が目的の画面（データ準備、実験一覧、候補比較など）では、段階的に開示して情報を絞る。初期状態で隠す列、折りたたんだセクションなどを使う。
- **例外:** 学習キューやパラメータ確認画面のように、利用者が値をすべて確認することが目的の画面では、情報を隠さない。グループ分けや見出しで見やすくし、隠す場合は利用者が自分で切り替えられる形にする。ここで入力欄や列を隠すときは事前にユーザーに確認する。

## 状態と安全性

- 押せないボタンには、押せない理由をツールチップか近くの文言で示す。
- 内部値（ID、enum 名、生のパス、例外メッセージ）をそのまま表示しない。利用者の言葉に置き換える。
- 確認ダイアログは、削除や上書きなど取り消せない操作にだけ出す。
- 時間のかかる処理は、進行状況と中断の方法を示す。

## レビューチェックリスト

レビューではスクリーンショットだけを見て、次を確認する。

- [ ] 各ボタンを押すと何が起きるか、コードを見ずに説明できる（実際の動作とずれていたら指摘として扱う）
- [ ] 主要な操作がどれか、一目で分かる
- [ ] 内部値や英語の識別子が表示されていない
- [ ] 押せないボタンに理由が示されている
- [ ] 用語が他の画面と揃っている
- [ ] 文言に冗長な言い回しがない
- [ ] 確認用の画面で、必要な情報が隠れていない
- [ ] アプリのテーマ（QSS）が適用された状態で撮影されている
