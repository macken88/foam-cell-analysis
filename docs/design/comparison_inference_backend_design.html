MockBackend は mock モードとテストのために残し、16.1 の新しい API の形に合わせて変更します。中身は今どおり合成値（評価値・予測は合成、ファイルは作らない）。GUI は mock と hybrid のどちらでも同じ呼び出しで動くこと。

2.4 本番推論画面との境界（hybrid 時）

本番推論は範囲外ですが、hybrid 時にも画面が落ちないようにします。

  • 適用モデルの決定（get_routing、resolve_model、list_released_models）は ComparisonService の実データを使う。
  • 推論結果（get_inference_result(filename, model_id)）は MockBackend の合成値のまま。今は self.released[model_id] を引いているので、モック内のリリースに依存しないよう、ファイル名と model_id の文字列だけから seed を作る形に変える。
  • 本番推論画面の表示・文言は変えない（画面はすでに仮の構成と明記されている）。

3. 検証用データセット

3.1 置き場所と読み込み

学習版と同じ構造（学習 3 章）で workspace/datasets/val_vNNN/ に置きます。dataset_info.json の purpose が val、status が RELEASED のフォルダを検証版とします。データ準備はモックなので、当面は次の方法で用意します。

  • scripts/generate_dummy_dataset.py に --purpose train|val と --version を追加する。val のときは usage=val、既定の seed を学習と別の値（1042）にし、is_dummy=true を残す。受け入れ確認用に val_v000（12 枚、分類A・B、空画像を含む）を作る。
  • 実データの検証版は、同じ構造で手作業で置けば読める（データ準備の実装で正式な作成口ができる）。
DatasetStore.list_versions(purpose: str = "train") -> list[str]      # 既定は今どおり train
DatasetStore.get_items(version: str, *, expected_purpose: str | None = None) -> list[DataItem]
DatasetStore.select_evaluation_items(version: str) -> list[DataItem]  # 3.2

読み込みの補強（学習版にも効く）: manifest.csv・metadata.csv に同じ item_id が 2 行以上あれば、その版を読めない版として一覧から外し、ログに理由を残す（今は辞書化で後の行が黙って勝つ）。版名とフォルダ名が一致しない版も外す。

3.2 評価対象

  • 検証版に収録された全画像を評価対象とする。学習時の分類・品質・usage の絞り込みは再適用しない。空マスクの画像も対象（AP の空の規則は学習 11 章）。
  • 順番は item_id の昇順。評価の run_spec に対象 ID の一覧を固定する。
  • チャンネル: 候補の実験設定の input_channels に一致しない画像があれば、除外せず評価前のエラーにする（「この検証用データセットには、モデルが使うチャンネル A がない画像があります」）。
  • 0 件の検証版はエラー。

3.3 評価の事前検査（評価プロセス内）

  1. dataset_info.json が purpose=val・RELEASED で、版名がフォルダ名と一致する。
  2. manifest と metadata が item_id で 1 対 1 に対応し、重複がない。
  3. manifest・metadata と、対象の画像・マスクの sha256 が一致する。
  4. 画像は 2 次元の uint8 / uint16、マスクは画像と同じ大きさの非負の整数ラベル。
  5. 候補の重み（final.pt）の sha256 が候補に記録した値と一致する。
  6. 保存済みの学習版・検証版の組を照合する（3.5）。新規評価では画像の重複検査を行わない。
  7. 予測の保存に必要な容量（Σ H×W×4 バイト + 1 GiB）が空いている。

1〜5・7 のどれかに失敗したら評価は failed。

3.4 旧評価の学習混入記録（互換性）

以下は schema 1 旧評価に保存された学習混入記録の読み取り規則です。現行の候補作成・評価では、確定時に検証画像の重複検査を完了した RELEASED な学習版と検証版の組を固定し、この検査を繰り返しません。

  • 比べるもの: 検証版の各画像の sha256（3.3 で照合済み）と、元の試行の run_spec.json の学習版で used_item_ids に含まれる画像の、manifest 上の sha256。
  • 結果は 3 値で result.json に保存する: none（重複なし）、found（重複あり。該当する item_id の組を記録）、unknown（学習版のフォルダが見つからない・読めない）。
  • schema 1 の found は履歴として閲覧できますが、新規リリースには使用できません。none または unknown は、候補の固定ペアと一致し、ほかのリリース条件を満たせば新規リリースに使用できます。これらの旧記録値を新しい評価で作成することはありません。
  • none の意味は「同じ内容のファイルの重複がない」ことだけである。同じ試料の別視野・切り出し違い・同じ撮影系列の画像は検出できない。試料単位の独立性はデータ準備（試料識別情報による確認。データ準備仕様 6 章）の責務とし、画面・記録では「同一画像の混入なし」と表示する（「独立性を確認済み」とは書かない）。

3.5 候補へ固定する検証版

候補作成時に、学習版が記録した base_validation_version と学習版・検証版双方の RELEASED 状態および版名を確認し、この学習・検証版の組を候補へ永続固定します。識別子と画像ハッシュの重複防止はデータセット確定時の責務です。旧候補の移行時に限り、その候補について一度重複検査を行います。候補は固定した検証版だけで評価します。

  • 学習版を確定した時点で記録した base_validation_version だけを候補に固定し、その版で評価する。
  • 候補一覧の検証版選択は候補を絞り込むだけで、評価先を変更しない。評価処理は引数として検証版を受け取らず、候補に固定された版でのみ評価する。
  • 旧候補は元学習版の識別子・ハッシュと履歴を一度照合し、安全に確定できる場合だけ固定値を補完する。照合不能・不一致は理由を記録し、評価と新規リリースを停止する。公開済み release は元の評価を保持し、新しい release を作らない。

4.1 書き込みの規則

  • 各ファイルの書き手は上の表記どおり 1 者に限る。「ComparisonService」は GUI プロセス内のサービスのことで、画面のウィジェットから直接ファイルを書かない。
  • JSON・CSV・PNG・TIFF・重みは、同じフォルダの一時ファイル（*.tmp）に書き、flush・fsync・close してから os.replace で置き換える。完成名へ直接書かない。
  • JSON は allow_nan=False。「対象なし」の AP は null。
  • events.jsonl は 1 行ずつ追記して flush する。読み手は途中で切れた最終行を無視する。
  • result.json は、全成果物の保存が終わった後に最後に書く。
  • Windows の一時的な共有違反（PermissionError）は、0.1 秒間隔で最大 5 回まで再試行してよい。それでも失敗したら失敗として扱う。
  • 記録するパスは基準フォルダからの相対パスだけ（学習 12.3 と同じ）。読むときは、絶対パス・..・ドライブ指定・基準フォルダの外へ出るパスを拒否する。
  • *.tmp と .preparing_* の削除は、起動時の復旧（7.6、13.3）だけが行う。

  • 固定値を、その時点のライブラリの既定値から補ってはいけない。学習時の評価パラメータが run_spec にない古い試行は、既知の旧形式として学習 10.2・10.3 の値を補い、補ったことを candidate.json に記録する。

5.3 候補の作成

TrainingService.create_candidate_snapshot(experiment_id, *, attempt: int) -> CandidateSnapshot
ComparisonService.add_candidate(experiment_id, attempt, inference_config_id, comment="") -> Candidate
  • 試行番号を明示する（今は最新の完了試行を自動で選んでいる。画面では候補追加ダイアログで試行を選ぶ。GUI 設計 7.2）。
  • 対象は status が completed の試行で、result.json が妥当なものだけ。
  • snapshot には final.pt の sha256 を含める（result.json の成果物一覧の値を使い、作成時に実ファイルのサイズと照合する）。
  • 候補 ID は RC-NNN の連番。フォルダは .preparing_<uuid> に candidate.json を書いてから改名して公開する。

5.4 同一性と fingerprint

  • 候補の fingerprint = sha256（重みの sha256、model_type、model_config、preprocessing、effective_params を正規化した JSON）。fingerprint が同じ候補（非採用を除く）がすでにあれば、推論設定 ID が違っても重複としてエラー（「既に RC-00x として登録済みです」）。
  • 評価の input_fingerprint = sha256（候補の fingerprint、検証版の manifest・metadata の sha256、対象 ID の一覧、metric の ID）。
  • JSON の正規化は json.dumps(sort_keys=True, separators=(",", ":"), ensure_ascii=False)。数値は float に揃えてから入れる（0.5 と 1/2 を区別しない）。

5.5 状態

保存する状態は candidate・rejected・released の 3 つです。「評価中」は保存せず、評価ジョブが実行中または待機中かどうかから表示時に導出します。評価中・待機中の候補は、非採用・リリースできません。

6. OOF AP の扱い

学習で保存している OOF 予測は、学習時の評価パラメータで確定済みのラベル画像です。閾値を変えた場合の OOF AP を、これから再計算することはできません。そこで次のようにします（仕様 17 章をこれに合わせて書き換える）。

candidate.json の oof = {
  "source_run_id": "exp_0001/attempt_001",
  "selected_epoch": 10,
  "evaluation": {overall: {ap, n_images}, per_class: {...}},   # 学習時の OOF（そのまま）
  "source_effective_params": {...},                           # 学習時の評価パラメータ
  "applicability": "matching" | "different" | "unknown",
  "reason": null | "推論設定が学習時と異なります" | "学習時の評価条件を確認できません"
}
  • matching: 候補の effective_params・前処理・入力の変換が、学習時の評価条件と一致する。比較は設定 ID ではなく、型を揃えた実効値で行う。
  • different: 一致しない。
  • unknown: 学習時の評価パラメータの記録がなく、判定できない（5.2 の補完をした場合もこれにする）。
  • 候補一覧と採用モデル一覧の「学習時 OOF AP」は、適用可否にかかわらず学習時の保存値を表示する。different/unknown は薄色にし、日本語の理由をツールチップで示す。これは再評価値ではなく、条件の異なる値を比較可能と示すものではない。
  • 詳細評価ダイアログとリリース記録には、applicability によらず「学習時 OOF AP（参考）」として値を残す。
  • OOF AP は fold ごとのモデルの評価であり、final.pt 自身の評価ではないことを、詳細評価ダイアログの注記に書く。
  • fold の selected.pt を使った再推論（推論設定を変えた OOF の再評価）は先送りする（20 章）。推論設定が異なる OOF 数値は学習時の参考値として表示し、適用可能な現評価と混同しない。

7. 評価の流れ

7.1 評価の準備（唯一の作成口）

ComparisonService.prepare_evaluation_run(candidate_id) -> PreparedRun
  1. 候補が candidate 状態で、検証版が存在することを確かめる（なければ ValueError）。
  2. 対象画像を決める（3.2）。チャンネル不一致はここで ValueError。
  3. evaluations/<版>/.preparing_<uuid>/ に run_spec.json を書く。
  4. 次の番号（eval_NNN）へ os.replace で改名する。ここで初めて評価として数える。

学習の prepare_training_run（学習 5.1）と同じ考え方です。再評価は常に新しい eval_NNN を作り、過去の評価は変更・削除しない。再評価が失敗しても、前回の成功した評価はそのまま使える。

7.2 起動とプロセス間の取り決め

学習 7.1〜7.3 と同じです（プログラムは sys.executable、引数は ["-m", "foam_cell_analysis.inference.run", "--run-dir", <絶対パス>]、hello → Job Object への登録 → process.json → go、stdin の EOF で終了、num_workers=0、中断は kill）。TORCH_HOME・CELLPOSE_LOCAL_MODELS_PATH も学習と同じ場所に固定する（学習済みの重みだけで推論できるので、通常はダウンロードは起きない）。

hello の pid は QProcess が返す pid と照合し、一致するか、その直接の子であるときだけ合格にする（venv の python.exe はランチャーで、実際の Python はその子として動くため）。どちらでもなければ起動失敗。Job Object にはランチャーを登録し、kill は登録後なら TerminateJobObject で行う。process.json には OS から得た実際のプロセス作成時刻を記録する（復旧時の照合用）。学習の起動も同じ規則にする。

7.3 評価プロセスの流れ

  1. run_spec を読む（不正なら終了コード 2）。hello → go を待つ → started。
  2. 事前検査（3.3）。resolved_data.json を書いて preflight を出す。
  3. モデルを組み立てる（8.1）。
  4. 対象画像を 1 枚ずつ: 読み込み → 前処理 → 推論 → 予測ラベルを保存 → AP のマッチング（match_counts）→ image_done。
  5. 集計（9 章）。per_image.csv・eval_counts.npz・instances.csv を書き、最後に result.json を書いて completed を出す。

どこで例外が起きても error.json を書いて error を出し、終了コード 1 で終わる。

7.4 イベント

外形（v, run_id, seq, time, type）と hello・started・warning・error・completed は学習 7.3 と同じ。評価固有のものは次のとおり。

type追加の必須項目意味

進捗イベントだけで成功を確定しない。成功は必ず result.json の検証（7.5）で決める。

stdout の扱いを学習と揃えて明確にする: hello より前の行は厳格に解釈し、不正なら起動失敗。hello 以降、JSON でない行は stdout.log に残して無視する。JSON として読めるが必須項目が欠けたイベントはプロトコルエラーとして評価を failed にする（学習側も新しい共通基盤に移すときに同じ規則にする）。

7.5 終端状態の判定

学習 5.2 と同じ優先順位を、共通の純粋関数（15.3）で判定します。「result.json が妥当」の中身だけが評価用です。

  • schema と run_id・evaluation_id・input_fingerprint が run_spec と一致する。
  • run_spec の対象 ID すべてに予測があり、ファイルが存在し、バイト数が一致する。
  • per_image.csv が存在し、行数が対象件数と一致する。eval_counts.npz と instances.csv が存在する。

判定の終了時に status.json を書く。ここではファイル内容の sha256 は再計算しない（重いので、抽出結果比較・出力・リリースの時点で必要な分だけ照合する。7.7）。

7.6 起動時の復旧

学習 5.4 と同じ手順を、全候補の全評価に対して行います（プロセスの照合 → 終端判定 → status.json、その後に *.tmp と .preparing_* を削除）。評価にはキューがないので、キューの修復はありません。復旧中に実行中だった評価は stopped（理由 interrupted または app_exit）になり、自動では再開しない。

7.7 採用する評価と破損

  • 候補一覧・詳細に出す評価 = その候補・その検証版で、status が completed かつ input_fingerprint が現在の条件と一致する評価のうち、番号が最も大きいもの。
  • 評価詳細・抽出結果比較・出力・リリースは、画面を開いた時点の evaluation_id を固定して使う（途中で再評価が終わっても、見ている結果が入れ替わらない）。
  • completed の評価の予測ファイルが後から消えた・変わった場合、status.json は書き換えない。読んだ時点で sha256 またはサイズが合わなければ、その評価を「破損」として扱い、比較・出力・採用に使わない（画面には「結果破損（再評価してください）」と表示する）。

10. 粒子分離（後処理）

ID は particle_split_symmetric8_v1。今の GUI（gui/widgets/image_convert.py の to_binary_separated）と同じ定義で、Qt に依存しない inference/particle_split.py へ移し、表示と出力で同じ関数を使います。

L = 入力ラベル画像（0 = 背景）
境界 D(p) = L(p) > 0 かつ、8 近傍のどれかの q で L(q) > 0 かつ L(q) ≠ L(p)
分離後 S(p) = 0（D(p) のとき）/ L(p)（それ以外）
二値   B(p) = 255（S(p) > 0）/ 0
  • 判定はすべて元の L で行い、一斉に背景化する（両側を削る）。反復しない。ラベル番号の大小に依存しない。
  • これで、残った画素の間に異なるラベル同士の 8 近傍接触は残らない。
  • 一方で、細い粒子が消える・1 つの粒子が分断されることはあり得る。面積・粒径が保たれることは保証しない。

10.1 検査と記録

出力時に画像ごとに次を数え、出力の記録（12 章）に残します。全体の連結成分数だけで正しさを判定しない（モデル出力のラベル 1 つが、元から複数の領域に分かれていることもあるため）。

  • 残った異ラベル接触の数（0 でなければ実装の不具合なので出力を失敗にする）。
  • 消えたラベル（分離後に面積 0）の数。
  • 分断されたラベル（分離前は 8 連結で 1 つ、分離後は 2 つ以上）の数。
  • 背景化した画素数と、前景に対する割合。

消失・分断があっても二値マスクは出力する（仕様どおり、後処理は固定アルゴリズム）。出力完了の案内に「消失 n 件・分断 m 件（詳細は export_report.csv）」を出す。

13. リリース登録

13.1 条件と記録

ComparisonService.release_candidate(candidate_id, evaluation_id, comment="") -> ReleasedModel

リリースできる条件: 候補が candidate 状態で評価中でない。指定した評価が completed で破損していない（予測の sha256 を照合）。候補に固定した検証版と評価の検証版が一致する。

release.json（schema=1）に固定する内容:

  • model_id（model_NNN の連番）、released_at、comment、app_version。
  • 重み: model.pt（release フォルダからの相対パス）、バイト数、sha256。元の試行の run_id と重みの相対パス（出典として）。
  • model_type、model_config、preprocessing、effective_params、inference_config_id。
  • 候補: candidate_id、candidate の fingerprint。
  • 検証評価: evaluation_id、validation_version、input_fingerprint、overall・per_class、metric。schema 1 から復旧する既存 release に限り旧 contamination を保持する。
  • OOF: 6 章の oof（applicability を含む）。
  • 外部解析結果: その時点の external.json の records（コピー）。
  • particle_split_id。

リリース後に設定を変える場合は上書きせず、新しい候補・新しいリリースを作る（仕様 11 章）。

13.2 公開の手順

  1. releases/.preparing_<uuid>/ を作る。
  2. 候補の final.pt を model.pt へコピーする（ハードリンクは使わない。元の実体への書き込みがリリースへ波及しないように）。コピー後に sha256 を計算し、候補の値と一致しなければ失敗。
  3. release.json を書く。
  4. 次の番号（model_NNN）へ os.replace で改名する。ここでリリースが成立する。
  5. candidate.json の status を released、released_model_id を設定する。

コピーの前に、コピーに必要な容量（重みのバイト数 + 100 MB）を確かめる。cpsam の重み（約 1.2 GB）は数十秒かかることがあるので、リリース登録はワーカースレッドで行い、進行中の表示を出す。リリースが途中で失敗したときは、その処理が作った準備フォルダをその場で削除する（大きな重みを次回起動まで残さないため。他の処理が作った準備フォルダは起動時の復旧だけが消す）。

再試行の規則（手順 4 と 5 の間で失敗した後の再登録）。新しい番号の採番と重みのコピーの前に、公開済みのリリースを調べる。

  • 同じ候補の公開済みリリースがあれば、今回指定した再評価 ID が異なっていても既存リリースを再利用し、公開時の元評価・コメントを保持したまま候補の status と released_model_id だけを修復する。release.json は書き換えず、戻り値には再利用を示す印を付ける。
  • 候補・リリースの参照が欠損または不一致の場合は、何も作らずエラーにする。別のリリースは作成しない。
  • 失敗時の後片付けで、公開済みのフォルダ（model_NNN）は削除しない。削除するのは、その処理自身が作った準備フォルダだけ。
  • 手順 4 の後で候補の保存が失敗したときは、登録の失敗ではなく「公開済みだが状態を保存できなかった」と利用者に伝える（実際に公開された状態と矛盾させない）。

13.3 復旧

起動時に releases/.preparing_* を削除する。公開済みリリース（model_NNN）について、参照する候補の status が released でなければ、既存 release.json が参照する元評価・リリースを維持したまま候補の status と released_model_id を修復する（4 と 5 の間で落ちた場合）。新しいリリースは作らない。候補とリリースの参照が食い違う場合は修復せず、ログに残す。

13.4 リリースの表示

リリース済みモデルの一覧・詳細・resolve_model は release.json だけで動くようにする（今のリリース画面は get_experiment で実験を引いているのでやめる）。

OOF AP の表示。release.json の oof.applicability と oof.reason を ReleasedModel（oof_applicability・oof_reason）へ引き継ぎ、実験は引かない。

  • 一覧は学習時 OOF AP の保存値を常に参考値として出す。different・unknown・記録がない旧形式は薄色にし、理由を日本語ツールチップで確認できる。これは現在の再評価値ではなく、OOF による最高値強調もしない。
  • 詳細（右の欄と「リリースの詳細を表示」）は数値を残し、「学習時 OOF AP（参考）」と明示する。条件（推論設定が学習時と異なります / 学習時の評価条件を確認できません）と、final.pt 自身の評価ではないことを併記する。

13.5 実験の削除との関係

今の参照保護（比較候補（非採用を除く）・リリース済みモデルから参照されている実験は削除できない。学習 12.3）は、ComparisonService の候補・リリースを見るように変えて維持する。リリースは重みを独立に持つので実験が消えても動くが、削除の許可を緩めるのは別の仕様変更とする。

14. モデル振り分け

routing.json = {
  "schema": 1,
  "revision": 12,
  "assignments": {"分類A": "model_003", "分類B": null},
  "history": [{"changed_at": "...", "revision": 12, "classification": "分類A",
               "before": "model_001", "after": "model_003"}]
}
  • 現在値と履歴を 1 つのファイルに置き、1 回の原子的な置き換えで更新する（2 ファイルに分けると食い違いが起きうる）。
  • apply_routing(changes, *, expected_revision: int) -> RoutingState。全変更を先に検証し（存在するリリースか、分類名が正しいか）、1 つでも不正なら何も変えずに ValueError。revision が現在値と違えば ValueError（「振り分けが別の操作で変更されました。画面を開き直してください」）。
  • 振り分けの対象となる分類 = 確定済みの全データセット版（学習・検証）に現れる分類 ∪ routing.json にすでにある分類。
  • resolve_model(classification): 未割り当て・分類なしは None。割り当て先のリリースが読めない（release.json の破損・model.pt の欠落）ならエラーにし、他のモデルへ自動で切り替えない。

15. ジョブの排他と共通基盤

15.1 ComputeCoordinator

class ComputeCoordinator(QObject):
    changed = Signal()
    def request(self, owner: str, label: str, start: Callable[[], None]) -> Ticket
    def release(self, ticket: Ticket) -> None
    def cancel(self, ticket: Ticket) -> None      # 待機中の要求を取り消す
    is_busy: bool
    active_label: str | None
    waiting: list[Ticket]
  • 学習（TrainingRunner）と評価（EvaluationRunner）は、開始前に request で占有を求める。空いていればすぐ start を呼び、使用中なら待ち行列（先着順）に入れる。実行中の処理に割り込まない。
  • 占有期間は準備 → 起動 → 実行 → 終端処理（status.json の保存）まで。終端処理が終わってから release する。終端処理の保存に失敗したら、次の待機要求を開始しない（学習 5.2 のキュー停止と同じ考え方。画面にエラーを出す）。
  • 学習キューの次の項目も、評価が実行中なら待つ（キュー表には「評価の終了を待っています」と表示する）。
  • 終端処理の保存に失敗したときは release(ticket, ok=False, error=…) で止まった状態にし、unblock() まで次を開始しない（is_blocked・blocked_error・wait_message(owner) で画面に理由を出す）。学習キューでは「すべて実行」を押すと解除する。評価側の解除は評価の開始操作で行う。
  • 複数候補の評価は、候補 1 件ごとに占有を取り、1 件ごとに返す（その間に学習の要求が来れば、先着順で学習が入る）。

15.2 EvaluationRunner

class EvaluationRunner(QObject):
    progressed = Signal(str)           # candidate_id
    ended = Signal(object)             # EvaluationOutcome(candidate_id, evaluation_id, status, message)
    def start(self, candidate_ids: list[str]) -> None
    def request_stop(self) -> None     # 実行中の 1 件を中断し、待機中の残りも取り消す
    def shutdown(self) -> None

終端処理は runner だけが 1 回だけ行う（学習 6.1 と同じ）。アプリ終了時は学習 6.3 と同じ手順（確認 → stop_request.json → kill → 最大 10 秒待つ）。終端処理の保存に失敗したときは、待機中の残りの候補を取り消して ended を出し（状態は「取り消し」）、調停役を止まった状態にする（15.1）。

19. 成果物の整理

記録は残したまま、不要になった大きなファイル（主に重み）だけを消して容量を空ける操作です。学習側の試行が対象です。自動では消さず、ユーザーが実験一覧から明示的に行います。比較側の評価結果（予測画像など）とリリース（releases/）は対象外で、消しません。

19.1 種類と条件

種類（category）ファイル（run_dir からの相対パス）消せる条件
fold_periodic: fold の定期保存モデルcheckpoints/fold_*/epoch_*.pt試行が確定している（status.json がある）
fold_selected: fold の選択エポックのモデルcheckpoints/fold_*/selected.pt同上。消すと、将来の OOF 再評価（20 章）ができなくなることをダイアログに書く
final: 最終学習モデルcheckpoints/final.pt同上。かつ、状態が「候補」（評価中・評価待ちを含む）の比較候補がこの試行を参照していない。非採用・リリース済みの候補だけが参照しているなら消せる（リリースは重みのコピーを持つ。13.2）
temporary: 中断・失敗した試行の一時ファイルtmp_pred/、tmp_ckpt/ の中身試行の状態が stopped / failed
  • いつも残すもの: 設定・run_spec・result・events・ログ・eval/・oof/・チェックポイントのメタ情報（*.pt.json）。
  • 学習中・待機中の実験は、どの試行も対象外。
  • 対象はシンボリックリンクをたどらず、run_dir の中の実在するファイルだけ（パスの逸脱は 4.1 と同じ規則で拒否）。

19.2 記録と手順

pruned.json = {
  "schema": 1,
  "entries": [
    {"path": "checkpoints/final.pt", "category": "final", "size": 180000000,
     "sha256": "…",                         # result.json の成果物一覧かメタ情報の値（なければ null）
     "state": "deleting" | "deleted",
     "requested_at": "…", "deleted_at": "…" | null}
  ]
}
  1. 消す対象を決め、pruned.json に state=deleting で追記して保存する（原子的な書き込み）。
  2. ファイルを消す（すでにない場合は消えたものとして扱う）。
  3. pruned.json の該当項目を state=deleted、deleted_at を入れて保存する。

起動時の復旧で deleting の項目があれば、2〜3 をやり直す。書き手は TrainingService だけ。

19.3 他の処理への影響

  • 試行の状態は変わらない（status.json は書き換えない。終端判定の result.json の検証は status.json がないときだけ行うので、整理の後に呼ばれることはない）。
  • 整理した final.pt からは候補を作れない（create_candidate_snapshot が「最終学習モデルは成果物の整理で削除されています」のエラーを返す）。
  • 実験の履歴を作り直すとき（学習 5.4）、pruned.json に載っているチェックポイントは「削除済み」として扱い、欠けていてもエラーにしない。実験詳細の途中保存モデル一覧に「削除済み」と出す。
  • 比較側は、候補の重みがないときの評価を事前検査で failed にする（19.1 の条件で通常は起きない）。
  • 実験の削除（学習 12.3）は今どおり。

20. 先送りした拡張

開発者との相談（2026-09-29）で、次の方向を最終形とすることにしました。ただし今回のブランチでは実装せず、次以降に回します。

  • OOF による推論設定の調整: 選択エポックの fold ごとの selected.pt で、各画像をその画像を学習に使っていない fold のモデルで推論し直し、推論設定を変えた OOF AP（調整後 OOF AP）を求める。save_fold_models=true の試行に限る。表示は「学習時 OOF AP」「調整後 OOF AP」「検証 AP」の 3 つに分ける。
  • 最終学習の分離: 学習の試行を CV までで完了できるようにし、比較モードで決めたエポック・推論設定から、学習側の独立したジョブとして最終学習を行う。推論設定だけを変えるなら最終学習はやり直さない。
  • エポックと推論設定の同時調整: 全 fold に重みが残っているエポックに限る。容量が大きい（cpsam・K=5 で 1 エポックあたり約 6 GB）ので、成果物の整理（19 章）と合わせて保持方針を決める。
  • 生出力の保存（再推論せずに閾値だけを変える）: Mask R-CNN の NMS 閾値は後から正確に再現できないなど制約が多いので、必要になってから Cellpose に限って検討する。

統計上の注意: OOF でエポックと推論設定を選ぶと、選んだ組み合わせの OOF AP は楽観的になる。検証 AP を見て選び直すと、検証データもモデル選択に使ったことになり、独立した評価とは呼べない。
