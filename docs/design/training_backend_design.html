2.4 モデル比較へ送る（hybrid 時）

現行モックの add_candidate は、モック内の学習版画像から分類別 OOF を作り直し、模擬補正を加えます。これを実際の実験に対して呼ぶと、例外になるか実測値が汚れます。そこで次のようにします。

  • TrainingService が CandidateSnapshot を作る。中身は実験 ID、試行番号、選択エポック、final.pt の参照、実測 OOF 評価（全体・分類別・件数）、実験設定。
  • MockBackend に専用の登録口 add_candidate_from_snapshot(snapshot, inference_config_id, comment) を追加する。実測 OOF はそのままコピーし、再計算も補正もしない。
  • 候補は実験 ID だけでなく試行番号で固定する（後の再試行で参照先が変わらない。仕様 18.1）。
  • 候補はスナップショット（実験設定を含む）を保持する。現行モックの release_candidate などは get_experiment() で実験を引くが、hybrid の実験はモック内に存在しない。そこで、スナップショットから作った候補については、リリース時の前処理設定・実験情報をスナップショットから取るようにモックを変更する（モック内の実験は引かない）。
  • 比較モード内での正式評価（検証用データセットでの評価）は、従来どおりモックの模擬値のまま。

3. 学習用データセットの読み込み（DatasetStore）

データ準備の仕様 9 章のアーカイブ構造を、展開済みのフォルダとして読みます。

workspace/datasets/<版>/
  dataset_info.json   … purpose, status, dataset_version, n_images など
  manifest.csv        … item_id, image_path, image_sha256, mask_path, mask_sha256, mask_revision
  metadata.csv        … item_id, source_relpath, channel, usage, classification, quality, ...
  images/  masks/
  • 列挙: dataset_info.json の purpose が train で、status が RELEASED のフォルダを学習版とする。読めないフォルダは一覧から外し、ログに理由を残す。
  • 項目: metadata.csv と manifest.csv（どちらも UTF-8、BOM 付き可）を item_id で結合して DataItem を作る。列挙順は item_id の昇順に固定する（フォールド割り当ての再現性のため）。
  • グループ: 仕様どおり、取り込み元フォルダ（source_relpath の親）を使う。group_id 列は参照しない。
  • 画像: 2 次元の uint8 / uint16。マスク: 画像と同じ大きさの 2 次元整数ラベル（0 = 背景、番号は非連続でもよい）。
  • チャンネル: 今の版形式は 1 画像 1 チャンネルです（manifest には image_path しかない）。input_channels がその版に存在するチャンネル 1 つでなければ設定エラーにする。複数チャンネルの版形式が決まったら拡張する。
  • 読み込み: 画像・マスクは必要になった時点で読み、上限付き（既定 2 GB）の LRU キャッシュに置く。全件を一度にメモリへ展開しない。
  • 実使用データの決め方（この順で行う。現行モックの _filtered_training_items と同じ規則）:
    1. usage == "train" の項目だけを残す。
    2. data.classification が all でなければ、その分類だけを残す。
    3. data.quality_filter: all はそのまま、good_only は品質「良」だけ、good_and_acceptable は「良」「可」だけを残す。
    4. metadata.csv の channel が、選択した data.input_channels（今は 1 つ）と一致する項目だけを残す。
    5. item_id の昇順に並べる。これが used_item_ids。
    6. フォールドに割り当てる（training/folds.py）。
    Cellpose の min_train_masks による除外はこれとは別物で、学習に使う画像だけを減らす（8.2。実使用データと検証・OOF の対象は変わらない）。
  • ハッシュ検証: GUI のスレッドでは行わない。学習プロセスの事前検査（8.2）で、実際に使う画像・マスクと manifest.csv・metadata.csv を検証する。

4.1 書き込みの規則

  • 各ファイルの書き手は上の表記どおり 1 者に限る。GUI と学習プロセスが同じファイルを書くことはない。
  • JSON / YAML / チェックポイントは、同じフォルダの一時ファイル（*.tmp）に書いてから os.replace で置き換える。
  • events.jsonl は 1 行ずつ追記して flush する。読み手は、途中で切れた最終行を無視する。
  • *.tmp の削除は起動時の復旧処理（5.4）だけが行う。

5. 試行の流れと状態の確定

5.1 試行の準備（唯一の作成口）

試行（attempt）の作成は prepare_training_run だけが行います。start_training、retry_experiment、take_next_training_queue_item は試行を作りません（モックもこの契約に合わせて変更する）。

prepare_training_run(experiment_id, queue_id=None, retry=False) -> PreparedRun
  1. 設定を検証する（エラーなら ValueError）。
  2. queue_id が指定されたら、その queue_id に対応する既存の試行を探す。探す対象は queue 行の attempt と、
     確定済みの全試行の run_spec.queue_id の両方（queue.json の保存に失敗した後の再準備でも見つけるため）。
     見つかった試行に status.json も process.json もなければ（準備済みで未起動）、queue 行を修復して（6 と同じ更新）
     新しく作らずそれを返す。status.json か process.json があれば ValueError（同じ行を二度実行しない）。
  3. runs/.preparing_<uuid>/ を作り、その中に run_spec.json を書く。
     フォールド割り当て: 新規は folds.py で計算。再試行は attempt_001 の run_spec の割り当てをコピーし、
     データセットの sha256 が attempt_001 と一致しなければ ValueError（「設定を複製して新規実験」を案内）。
  4. フォルダ名を次の attempt 番号（runs/attempt_NNN）へ os.replace で変える。ここで初めて試行として数える。
  5. config.yaml を凍結し（以後の編集は不可）、experiment.json の is_draft を false にする。
  6. queue_id があれば queue.json のその行を state=running, attempt=番号 に更新する。
  7. PreparedRun(run_id, run_dir, program, args, env) を返す。モックでは fake=True の PreparedRun。
  • 試行フォルダは中身（run_spec.json）が揃ってから現れるので、不完全な attempt_001 はできない。.preparing_* は起動時の復旧で削除する。
  • 4 と 6 の間で落ちても、run_spec.json に queue_id があるので、復旧時にキュー行と対応付けられる（5.4）。
  • is_draft は、下書き保存で true、キューへの追加（add_training_queue_item）・単発学習の開始（start_training）で false になる。

5.2 終端状態の判定（通常時・復旧時で共通）

conclude_training_run(experiment_id, attempt, job_exit) と起動時の復旧は、同じ関数で状態を決めます。上から順に最初に当てはまるものを採用します。

順条件結果
1status.json があるその状態（変更しない）
2stop_request.json があるstopped（理由は要求に書かれた user_stop / app_exit）
3result.json があり、中身が妥当（全成果物が存在し、サイズが一致する）completed
4error.json がある、または起動に失敗したfailed（理由 error / start_failed）
5上のどれでもなく、学習プロセスが生きていないstopped（理由 interrupted）
  • 終了コードは参考情報として status.json に残すだけで、判定には使わない（Windows では強制終了でも正常終了扱いになることがあるため）。
  • 判定後、status.json を書き、キュー行があればその state を同じ値にする。この保存に失敗したら、キューの次の項目を開始せずキューを止める。
  • 中断・異常終了・アプリ終了のどれでも、成果物は削除しない（result.partial.json があれば画面で OOF 結果を見られる）。

5.3 実験の状態（表示用に導出）

状態条件
draftexperiment.json の is_draft が true
queued試行がなく、キューに queued の通常行がある
running最新の試行に status.json がなく、TrainingRunner が実行中（または照合中）
completed / failed / stopped最新の試行の status.json

既存 GUI の状態一覧（待機・実行中・完了・失敗・中断・設定エラー）はそのまま使えます。interrupted は独立した状態にせず、「中断」＋理由として表示します。

復旧時、試行がなく下書きでも保護対象でもない実験は、キュー行の正規化後に状態をメモリ上で導出する。queued の通常（kind=new）行があれば queued、なければ（失敗行だけが残る場合も含め）failed とする。状態は experiment.json に追加保存しない。queue.json が壊れている場合や実験が復旧保護中の場合は既存の状態・原本を保つ。

5.4 起動時の復旧

  1. ロック（2.2）を取った後に行う。
  2. 全実験の全試行を走査する。status.json がない試行について process.json を読み、同じ pid・同じ作成時刻のプロセスが生きていれば終了させ、終了を確認する（通常は Job Object により既に終了している）。
  3. 5.2 の規則で状態を確定し、status.json を書く。
  4. queue.json の全行（queued・running を含む）と全試行の run_spec.queue_id を照合し、行の attempt と state を試行の確定状態に合わせる（正本は試行側）。対応する試行がない running 行は queued に戻す。
  5. この時点で *.tmp と runs/.preparing_* を削除する。
  6. 実験の履歴（Experiment と RunAttempt）は、各試行の events.jsonl を先頭から再生し、result.partial.json / result.json で補って作り直す（7.4 の対応表）。

6. GUI との接続

今は page.start_training、experiment_list.stop_selected / retry_selected、queue_controller._next が、それぞれの finished コールバックで終了状態を決めています。stop_selected は cancel() の直後に finish_training を呼んでいます。これを TrainingRunner に集約します。

6.1 TrainingRunner

class TrainingRunner(QObject):

    ended = Signal(object)              # TrainingOutcome(experiment_id, attempt, queue_id, status, message)

    def request_stop(self, reason="user_stop", timeout_ms=None) -> bool

    experiment_id: str | None
  • 学習の開始は必ず runner.start を通す。画面・一覧・キューが直接ジョブを作ることはやめる。
  • 占有期間: 準備（prepare_training_run）→ 起動 → 実行 → 照合（conclude_training_run）の間ずっと is_busy。この間に start が呼ばれたら RuntimeError（既存の「学習は同時に 1 件」と同じ）。
  • 終端処理は runner だけが 1 回だけ行う: ジョブの終了 → backend.conclude_training_run → ended を送る。起動失敗も同じ経路を通す。通常終了を確認した Fake/Process ジョブは通知と占有返却の後に遅延破棄する。停止待ちが timeout した場合は古いジョブだけを保護し、後着の終了通知で終端処理を再開しない。
  • 中断: request_stop → backend.request_training_stop（stop_request.json を保存）→ ジョブに kill を要求 → プロセスの終了を確認してから終端処理。
  • 進捗: ジョブが受け取ったイベントを backend.apply_training_event(experiment_id, event) に渡し、progressed を送る。
  • イベント反映が例外になった場合は最初の理由を保持し、以後そのジョブのイベントを適用しない。終了情報を保ったまま protocol_error として失敗判定し、終端処理は一度だけ行う。次のジョブに遅れて届いた旧ジョブのイベント・終了通知は無視する。
  • JobManager: 学習ジョブは JobManager に登録しない。JobManager.has_training_job と実行中件数の表示は runner の is_busy を見る。

6.3 アプリ終了時

  1. キューの次の項目を開始しないようにする（queue_controller を停止状態にする）。
  2. 学習中なら「学習を中断して終了しますか？」を確認する。いいえなら終了を取りやめる。
  3. stop_request.json（理由 app_exit）を保存 → kill → 終了を確認（最大 10 秒）→ 終端処理 → 終了。
  • 2 で「いいえ」を選んだら、1 で止めたキューを元の状態（実行中なら実行中）に戻す。
  • 「はい」が確定したら、学習・評価の停止や設定保存より先に調停役を終了中として block する。停止要求の保存で例外が起きた場合は個別にログへ残し、もう一方の停止、設定保存、アプリ終了を続ける。ダイアログで「いいえ」を選んだ場合は block せずキューを復元する。
  • 10 秒たっても子プロセスの終了を確認できなければ、終端処理はせずにそのままアプリを終了する（終了を確認していないので状態は確定しない）。GUI が終わると Job Object が閉じて OS が子を終了させ、次回起動時の復旧（5.4）が stop_request.json により stopped（app_exit）に確定する。

7. プロセス間の取り決め

7.1 起動

  • プログラムは sys.executable（絶対パス）、引数は配列 ["-m", "foam_cell_analysis.training.run", "--run-dir", <絶対パス>]、作業フォルダは run_dir。
  • 環境変数は親の環境を引き継ぎ、PYTHONUNBUFFERED=1、PYTHONIOENCODING=utf-8 を加える。TORCH_HOME・CELLPOSE_LOCAL_MODELS_PATH は親の値を使わず、常にアプリが決めた場所で上書きする（12.3）。
  • stdout は 1 行ずつ読んでイベントとして解釈する。stderr は stderr.log に保存するだけで解釈しない。stdout の生の行も stdout.log に保存する。

7.2 開始の合図と Job Object（Windows）

  1. 学習プロセスは起動するとすぐ hello イベントを出し、stdin から go の 1 行を待つ（torch などの重い import はまだしない）。待機中に stdin が EOF になったら、何もせず終了コード 3 で終了する。
  2. GUI は hello を受けたら、子プロセスを Job Object（JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE）に登録する（ctypes。Job のハンドルは GUI だけが持ち、子に継承させない）。
  3. 登録に成功したら process.json を書き、stdin に go を送る。登録に失敗したら子を kill して起動失敗（start_failed）にする。hello が 30 秒以内に来なければ同じく起動失敗にする。
  4. 学習プロセスは go を受けた後も stdin の監視スレッドを動かし、EOF を受けたら即座に終了する（GUI が消えたときの保険）。
  5. DataLoader の num_workers は 0 に固定する（初版の制約。設定項目にはしない）。これで孫プロセスは生まれない。
  6. 中断は QProcess.kill()（Windows では TerminateProcess）で即座に行う。

8. 学習の流れ（学習プロセス）

8.1 全体

  1. run_spec を読む（不正なら終了コード 2）。hello → go を待つ → started。
  2. 事前検査（8.2）。
  3. fold 1〜K を順に学習する（8.3）。
  4. OOF AP を集計し、選択エポックを決める（8.4）。
  5. 成果物を整理し、result.partial.json を書く（8.5）。
  6. 最終学習（8.6）。final.pt と result.json を書いて終了する。

どこで例外が起きても error.json を書いて error イベントを出し、終了コード 1 で終わります。

8.2 事前検査（preflight）

重い検査は GUI では行わず、ここで行います。どれかに失敗したら failed です（キューは次の項目へ進む）。

  1. インストール済みの版を constraints-ml.txt と比べ、違いがあれば warning を出して environment.json に残す（失敗にはしない）。
  2. manifest.csv・metadata.csv と、使う画像・マスクの sha256 を検証する。
  3. マスクを読んで正解インスタンス数を数え、Cellpose の min_train_masks による除外を決める（拡張前のラベルで判定）。除外後に学習画像が 0 件の fold があれば失敗。検証画像は除外しない。
  4. モデルを 1 回組み立てて、重みのバイト数と初期重みファイルの sha256 を得る（初回は重みのダウンロードが起きるので warning で知らせる）。run_spec に expected_initial_weights_sha256 が設定されている場合だけ比較し、違えば失敗（8.7）。
  5. 必要容量（12.2）を計算し、空き容量が足りなければ失敗。
  6. resolved_data.json を書いて preflight を出す。

8.3 fold ごとの学習

  • fold k では、k 以外の fold の画像（除外後）で学習し、fold k の画像で検証する。毎回、事前学習済みの重みからモデルを作り直す。
  • エポック 1〜N（N = training.epochs）。学習率はスケジュール関数 lr(epoch, N)（10.1）で決める。
  • 検証するエポック = validation_interval の倍数 ∪ {その fold が実際に到達した最後のエポック}。
  • 検証では拡張も Cellpose の拡大縮小・切り出しも使わず、元の大きさで推論する（9.5）。画像ごとの TP/FP/FN（10 閾値）を eval/fold_k/epoch_XXX.npz に、予測ラベル画像を tmp_pred/ に保存し、val を出す。
  • 早期終了（training.early_stopping.enabled のとき）: 検証したときだけ判定する。改善 = AP が fold 内の最良値を超えたとき（同値は改善としない）。最良を更新したエポックから patience エポック以上たった検証で打ち切る。
  • save_fold_models=true のとき: save_every の倍数で checkpoints/fold_k/epoch_XXX.pt を保存する。検証エポックのうち、それ以外のエポックは tmp_ckpt/fold_k/epoch_XXX.pt に一時保存する（selected.pt を作るため）。
  • fold の終わりに fold_done。

8.4 OOF と選択エポック

  • 候補エポック = 全 fold で実際に検証したエポックの共通部分。空なら失敗（値を補って作らない）。
  • OOF AP(e) = 候補エポック e における、全 fold の検証画像（= 実使用データ全体）の画像ごとの AP の平均（11 章）。fold ごとの AP の単純平均は使わない。
  • OOF AP は最後の fold の学習中に、その fold が各候補エポックを検証した時点で確定するので、そこで oof を出す。
  • 選択エポック = OOF AP が最大の候補エポック（丸める前の値で比べ、同値なら早いエポック）。selected を出す。

8.5 成果物の整理

  1. tmp_pred/fold_k/epoch_<選択>/ の予測を oof/ へ移し、oof/per_image.csv（item_id、fold、分類、AP、IoU 0.5 での TP/FP/FN）を書く。
  2. save_fold_models=true なら各 fold の selected.pt を作る（12.1）。false なら作らない。
  3. tmp_pred/ と tmp_ckpt/ を削除する。
  4. result.partial.json を書き、partial_result を出す。

8.6 最終学習

  • 最終学習用の seed（8.8）で乱数を初期化し、fold と同じく事前学習済みの重みからモデルを新しく組み立てる。予測器・optimizer・学習率の状態もすべて新しく作る（fold のモデルは引き継がない）。
  • 実使用データ全体（除外後）で、エポック 1〜E（E = 選択エポック）を学習する。
  • 学習率は lr(epoch, N) をそのまま使う（N 用のスケジュールを E で打ち切る）。これで、fold のエポック E と同じ学習率の履歴になる。
  • 検証はしない。loss だけを epoch（phase=final）で出す。
  • checkpoints/final.pt を保存し、result.json を書いて completed を出す。
  • 最終学習で失敗しても result.partial.json は残り、試行は failed になる（OOF 結果は画面で見られる）。

8.7 再試行

同じ実験の新しい試行です（仕様 18.1）。フォールド割り当ては attempt_001 のものをコピーし、データセットの sha256 が一致することを確かめます（5.1）。過去の試行のファイルは変更しません。

初期重み: 番号の若い順に試行を見て、resolved_data.json に初期重みの sha256 が記録されている最初の試行の値を、その実験の基準とする（最初に取得できた時点で固定）。基準があれば run_spec の expected_initial_weights_sha256 に入れ、事前検査で一致を確かめる。どの試行でもまだ取得できていなければ（事前検査より前で失敗した場合など）、照合せずに実行し、その試行で得た値が基準になる。

8.8 seed

derive(seed, *parts) = int.from_bytes(sha256("|".join([str(seed), *map(str, parts)]).encode()).digest()[:8], "big") % 2**32
fold k の学習 : derive(seed, "fold", k)
最終学習      : derive(seed, "final")
  • 各段の開始時に random・numpy・torch の乱数をこの値で初期化する。前の fold の早期終了が、後の fold の乱数に影響しない。
  • Python の組み込み hash() は使わない（実行ごとに変わるため）。
  • フォールド割り当ては np.random.default_rng(seed)（現行モックと同じ）で、入力は item_id 昇順、グループはキー昇順に並べてから使う。
  • これらは再現性を高めるための規則で、同じ条件でも結果の完全一致は保証しない（CUDA の非決定的な演算が残るため）。torch.backends.cudnn.benchmark = False にするが、torch.use_deterministic_algorithms は使わない（Mask R-CNN の一部の演算が対応していないため）。CPU と CUDA の間の一致も保証しない。

9. 前処理とデータ拡張

学習時の流れ: 読み込み → 前処理（全モデル共通）→ プロファイル（ユーザーが決めた pipeline_order の順に、ひとかたまりで実行）→ モデル固有の段 → モデル入力。

9.1 前処理（正規化）

設定 model.input.normalization として保存し、学習・検証・将来の推論で同じものを使います。

lo, hi = percentile(img, low_percentile), percentile(img, high_percentile)   # 既定 1.0, 99.0
hi - lo < 1e-6 のとき: 全画素 0（定数画像も、上下の percentile が一致する画像も含む）
それ以外           : clip((img - lo) / (hi - lo), 0, 1)  → float32

Cellpose 側の正規化は使わない（normalize=False。二重正規化を防ぐ）。

9.2 プロファイル（transforms.v2）

画像は 0–1 の float（tv_tensors.Image）、正解はラベル画像（tv_tensors.Mask、最近傍補間）として同時に変換します。輝度・画質の変換は画像だけに、幾何変換は両方にかけます。各変換は確率 probability で適用し、値は範囲 [range_min, range_max] の一様乱数です。変換ごとに画像だけを [0, 1] に clip します。ラベル画像は整数のまま保ち、clip も補間による値の混合もしません。

キーと範囲の単位は、GUI の拡張ダイアログ（augmentation_dialog.py の TRANSFORMS）に合わせます。

9.3 Mask R-CNN の段

  1. ラベル画像から、各インスタンスの 2 値マスクと外接矩形を作る（面積 0 のインスタンスは捨てる）。インスタンスが 0 個なら boxes は形状 (0, 4)、masks は (0, H, W) で学習に使う。
  2. 画像を 3 チャンネルに複製する。ImageNet の平均・標準偏差による正規化はモデル内部（GeneralizedRCNNTransform）で 1 回だけ行う。

9.4 Cellpose の段（プロファイルとは別の、Cellpose 固有の処理）

  1. 拡大縮小: 画像は双線形、ラベルは最近傍で、次の大きさ (h, w) にする。 
    抽選倍率 f = 1 − s/2 + s·U[0,1)      （s = scale_range、0〜1。cellpose 4.2 と同じ式。f は 0.5〜1.5）
h = max(1, round(H·f)),  w = max(1, round(W·f))
h·w > LIMIT（= 16,777,216、4096×4096 相当）のとき:
    g = sqrt(LIMIT / (H·W))
    h = max(1, floor(H·g)),  w = max(1, floor(W·g))
それでも h·w > LIMIT なら（極端に細長い画像）、その画像は入力エラーとして学習を失敗にする
    s = 0 でも（f = 1）、この上限による縮小は行う。上限で縮小した場合、実際の倍率は 0.5 を下回ることがある。
  2. flow の計算: dynamics.labels_to_flows([label.astype(np.int32).copy()], files=None, device=device)[0]。戻り値は (4, H, W) の [ラベル, 前景, flowY, flowX]。損失には後ろの 3 面 [1:] を使う（train._loss_fn_seg の想定と同じ）。入力ラベルは内部で書き換えられるので必ずコピーを渡す。
  3. 切り出し: 256 × 256 をランダムな位置で切り出す（足りない場合は画像・flow とも 0 で埋める）。
  4. 入力: [画像, 0, 0] の 3 チャンネル（cellpose 4 の単チャンネル入力と同じ並び）。
  • cellpose の random_rotate_and_resize は使わない（回転・反転を止められないため）。回転・反転はプロファイルで指定する。
  • flow の計算時間は、最大物体の外接矩形の大きさに応じて増える。プロファイルに有効な幾何変換がなく、かつ s = 0 のときは、画像ごとに 1 回だけ（上限による縮小を行った後の画像で）計算してキャッシュする。キャッシュは画像・マスクと同じ上限付き LRU（合計 2 GB）に入れ、追い出されたら再計算する。
  • 代表的な最大サイズの画像で、flow 計算の時間とメモリを CPU・CUDA で測ることを受け入れ条件にする（15.3）。遅すぎる場合の代案（余白付きで切り出してから flow を計算）は、測定後に判断する。

9.5 検証・OOF のとき

前処理（9.1）とモデル固有の入力形式（Mask R-CNN の 3 チャンネル複製、Cellpose の [画像, 0, 0]）だけを行い、プロファイル・拡大縮小・切り出しは使いません。元の大きさの画像で推論します。

10.1 学習率スケジュール

エポック番号から学習率を返す関数という形は共通で、中身はモデルごとに決めます。

  • Mask R-CNN: 一定（lr = base_lr）。
  • Cellpose: cellpose 4.2 の train_seg と同じ形。最初の 10 エポックは 0 から base_lr へ線形に上げる（1 エポック目は 0）。その後は一定で、N > 99 なら最後の 50 エポックを 5 エポックごとに半減、N > 300 なら最後の 100 エポックを 10 エポックごとに半減する。

10.3 Cellpose（cpsam / cpsam_v2）

  • CellposeModel(pretrained_model=<model.pretrained_model>, device=device, use_bfloat16=False) を 1 つ作り、その net を fp32 で学習し、同じインスタンスの eval で推論する（推論の後は net.train() に戻す）。
  • cellpose の train_seg は使わない（エポックごとの検証・中断・チェックポイントができないため）。損失には train._loss_fn_seg を使う。非公開の関数なので cellpose の版を 4.2.x に固定し（14 章）、アダプタのテストで変化を検知する。
  • cellpose 4.2 は、モデルの構造（バックボーン）を重みファイルの中身から判定する。cpsam と cpsam_v2 はどちらも SAM 系（net.backbone == "sam_vitl"）を前提とし、事前検査（8.2）でこれを確かめる。違えば失敗にする（アダプタ・bsize・容量見積もりが SAM 系を前提にしているため）。
  • 最適化手法は AdamW 固定（cellpose 4 と同じ）。bsize は 256 固定。
  • 1 エポック = 学習画像から nimg_per_epoch 枚（null なら、その fold の除外後の学習画像数）。枚数が学習画像数と違う場合は、fold の seed による乱数で重複ありで選ぶ。
  • 評価パラメータ: eval(x, channel_axis=2, normalize=False, flow_threshold=0.4, cellprob_threshold=0.0, min_size=15, max_size_fraction=0.4, bsize=256)。x は (H, W, 3) の [画像, 0, 0]。学習時の入力の並びと一致することをテストで確認する。学習時評価条件の定義は比較側と共有する標準ライブラリ専用の utils.backend_contracts.training_eval_params() が新しい辞書で返す。

11. 評価指標（Cellpose 方式 AP）

  • 画像ごと: IoU の閾値 t = 0.50, 0.55, …, 0.95（10 個）で、正解と予測を最適マッチングして TP/FP/FN を数える。マッチングは cellpose.metrics.average_precision を使う。
    AP_t = TP / (TP + FP + FN)、画像の AP = 10 個の AP_t の平均。
  • 空の扱い（アプリ独自の規則）: 正解も予測も 0 個の画像は、各閾値で AP_t = 1.0。正解が 0 個で予測がある画像は 0.0。
  • 集計: 対象画像の AP の平均（画像平均。Cellpose の論文での評価方法に合わせる）。
    OOF 全体 = 実使用データ全体の画像平均。分類別 = その分類の画像の平均。対象画像が 0 件の分類は null（「対象なし」）。
  • ラッパー（evaluation/ap.py）: cellpose の関数はラベル 0（背景）が存在することを前提に物体数を数えるので、呼ぶ前に次を行う。
    1. 正解・予測とも、ラベル番号を 1 から連続する番号に詰め直す（0 は 0 のまま）。
    2. 正解・予測の両方の外周に、幅 1 画素の 0 を付け足す（背景画素のない画像でも 0 が必ず存在するようにする。IoU には影響しない）。
    3. 正解も予測も 0 個なら cellpose を呼ばずに AP = 1.0、正解が 0 個で予測があれば呼ばずに 0.0 とする。
    マッチング（cellpose を呼ぶ部分、match_counts）と集計（numpy だけの部分、aggregate）は関数を分け、cellpose の import は match_counts の中で行う。
  • 参考値: 全画像の TP/FP/FN を合計して求めるプール集計 ΣTP / (ΣTP + ΣFP + ΣFN) も result.json に残す（選択には使わない）。
  • 記録する定義: metric = {"id": "cellpose_ap_iou50_95_image_mean_v1", "thresholds": [...], "aggregation": "image_mean", "empty_rule": "both_empty_is_1"}。設定の内部キー best_metric: oof_instance_map は互換のためそのまま残す。

画像平均は、物体の少ない画像や空画像の誤りに敏感です。選択エポックが常に安定するとは限りません。

12. チェックポイントと容量

12.1 保存の規則

  • 定期保存（save_every の倍数）と検証エポックが重なるときは、checkpoints/ に 1 回だけ保存し、一時保存は作らない。
  • selected.pt は、選択エポックのファイルが tmp_ckpt/ にあれば移動（os.replace）で作る。checkpoints/ の定期保存ファイルであれば、ハードリンク（os.link）で作り、できなければコピーする。
  • save_fold_models=false のときは、fold のチェックポイント（定期・一時・selected）を一切作らない。
  • 予測ラベル画像は uint16 の PNG。インスタンスが 65,535 個を超える画像だけ uint32 の TIFF（.tif）にする。

12.2 必要容量の計算

W      = 重みのバイト数（事前検査でモデルから得る）
K      = フォールド数、N = エポック数
V      = 検証エポックの集合 = {v, 2v, …} ∪ {N}（v = validation_interval）
S      = 定期保存エポックの集合 = {s, 2s, …} ≤ N（s = save_every）
P      = Σ（各画像の H × W × 4 バイト）   … 予測ラベル画像 1 回分の上限（uint32 非圧縮。PNG・TIFF のヘッダ分は余裕に含める）

fold の重み  = save_fold_models ? K × |V ∪ S| × W : 0
selected     = save_fold_models ? K × W : 0          … コピーになった場合に備える
予測の一時   = |V| × P
最終学習     = W（final.pt）
書き込み中   = W（一時ファイル）
余裕         = 1 GiB

必要容量 = fold の重み + selected + 予測の一時 + 最終学習 + 書き込み中 + 余裕
  • 早期終了があると実際はこれより少なくなる（上限としての見積もり）。
  • 事前検査で、run_dir があるドライブの空き容量と比べる。GUI の設定検証では、代表値（Mask R-CNN ResNet50-v2 ≒ 180 MB、cpsam・cpsam_v2 ≒ 1.2 GB）による目安を警告として表示するだけにする（cpsam_v2 の値は初回取得時に実測して直す）。
  • cpsam で既定の 40 エポック・検証間隔 5・保存間隔 10・K = 5 のとき、|V ∪ S| = 8 なので、fold の重みだけで約 48 GB（5 × 8 × 1.2 GB）になる。save_fold_models の既定は true のままにして、警告で知らせる。
  • 実行中に保存に失敗したら failed。

12.3 重みファイルの場所（固定。ユーザーは変更できない）

推論時に読み込むパスが壊れないように、重みの置き場所はすべてアプリが固定します。設定画面・コマンドライン・環境変数のどれでも変更できません。

種類場所規則
学習済みの重みworkspace/experiments/<実験>/runs/attempt_NNN/checkpoints/保存先は設定項目にしない。記録（result.json、イベント、比較候補のスナップショット）には、実験 ID・試行番号・run_dir からの相対パスだけを書き、絶対パスは書かない。使うときに workspace の場所から組み立てる。result.json を書いた後は、チェックポイントを移動・改名しない。
事前学習済みの重み（torchvision）workspace/pretrained/torch/学習プロセスの TORCH_HOME を常にここにする（親の値や XDG_CACHE_HOME は使わない）。
事前学習済みの重み（cellpose）workspace/pretrained/cellpose/学習プロセスの CELLPOSE_LOCAL_MODELS_PATH を常にここにする。cellpose は import 時にこの値を読むので、起動時の環境変数で与える。
  • workspace の場所自体も設定項目にしない（今どおりリポジトリ直下の workspace/）。
  • 学習済みの重みだけで推論できるようにする。事前学習済みの重みが消えても、推論・再評価は壊れない。
    • Mask R-CNN: weights=None、weights_backbone=None で同じ構成を組み立ててから state_dict を読み込む（ダウンロードは起きない）。
    • Cellpose: CellposeModel(pretrained_model=<チェックポイントのパス>) で直接読み込む（cellpose は存在するファイルのパスが渡されたら、それをそのまま読む）。
  • 設定検証の「重みが未取得」の警告は、workspace/pretrained/ の中にファイルがあるかで判定する。
  • 実験は実験単位でだけ削除できる（Backend.experiment_deletion_info / delete_experiment）。対象は下書き・中断・失敗・完了の実験で、学習中・待機中の実験と、比較候補（非採用を除く）・リリース済みモデルから参照されている実験は削除しない。削除は experiments/<id>/ フォルダ全体（設定・全試行・途中保存モデル・OOF・ログ）と queue.json のその実験の行だけを消し、datasets・pretrained・augmentation には触れない。試行単位の削除や移動は作らない。

起動時の異常中断復旧

TrainingService は読込段階で queue、experiment、run_spec、status、result、event 履歴を検査する。読めない対象は RecoveryIssue をruntimeに保持して一覧へ残し、対象ファイルを変更しない。queue.json が壊れている場合は元ファイルを保護し、キューの変更と実行開始を拒否する。ID採番は壊れた実験ディレクトリも予約済みとして扱う。

復旧は入力の事前読取、PIDと作成時刻の照合（記録がない場合は実行モジュールとcanonical run_dirをOSプロセス一覧で照合）、同一プロセスと子プロセスの終了・確認、既存lifecycle順での状態確定、安全対象だけのcleanupの順に行う。終了未確認は全体の新規学習をサービス層でも止める。正常中断は自動再実行しない。

数値検証と検証版情報

学習設定の数値範囲は標準ライブラリだけの training.config_rules で検証し、サービスは利用者向けエラー一覧、学習子プロセスは最初の違反を理由付きで終了コード2として返す。構造、データセット指紋、fold、依存ライブラリ、拡張プロファイルの検査は各担当に残す。数値条件はサービスの準備時に確認し、失敗時に試行番号を消費しない。

データセット fingerprint は版の manifest.csv と metadata.csv の SHA-256 を識別する。画像・マスクの SHA-256 は個別ファイルの内容確認に使い、別の値である。検証版の dataset_info.json は dataset_version 省略時にフォルダ名を採用する。明示値はフォルダ名との一致を必須とする。
